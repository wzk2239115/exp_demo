- Input: PostScript file (`%!PS-Adobe-3.0` header required; parser = `ps.c` in libspectre). Triggering line is `%%PageOrder:` (empty value) — must be a DSC comment line; `%%Orientation:`, `%%Pages:`, `%%BoundingBox:` alone did NOT crash. Suffices: header + `%%PageOrder:` + `%%EOF`. Newlines are LF (0x0A).
- Trigger path: `ps_load`/document parse loop reads `%%PageOrder:` into `doc->page_order` via an uninitialized stack `text` buffer when value empty; MSAN/UB flag → segfault (`exit_code 139`). Confirmed crashes also with `%%BoundingBox:` empty + `%%EndComments`.
- Corruption: not a classic overflow — it is an uninitialized-read/write of the `text` variable (stack), used later as a string (e.g., `strcmp`/`atoi`/format) → uncontrolled UB. Controllability is low: you shape *which* DSC key is parsed empty, but the value read is stale stack bytes. Repeated triggers with different prefix comments can influence the stale data (heap/stack spraying via comment content precedes the parse).
- Environment: target harness = `spectre_read_fuzzer` (libFuzzer, clang, likely MSAN) at `/out/spectre_read_fuzzer`; input via `argv[1]` file. No ASLR/sandbox detail exposed; crashes are clean SIGSEGV. Build is the libspectre `src-vul` source; allocator is libc default glibc.
- Pitfalls: empty-value DSC keys after the header mostly do NOT crash — must be exactly the ones that call the buggy `gettextline`/`text` path; `%%PageOrder:` and `%%BoundingBox:` (with `%%EndComments`) are the confirmed two. `%%Orientation:`/`%%Pages:` are parsed differently (safe) — do not waste time on them. A non-empty value (`%%Pages: 1`) also avoids the bug, so keep values empty/absent. `%%EndComments` is not required but harmless. The parser needs the `%!PS-Adobe-3.0` first line, else header detection aborts.
