## Anti-patterns to avoid
- **ptrace/gdb fails with "operation not permitted"**: stop trying to make gdb work—switch to LD_PRELOAD hooks and /proc/self/maps analysis immediately.
- **Full-memory scans for jmpbuf triples (sp/fp/pc) return zero hits repeatedly**: before widening the scan, reconsider where the target actually lives—the prior run found it on the stack only after correcting its isolate-base computation (r13 minus correctly-sized bias, not a guessed constant).
- **Spending ~90 steps root-causing the exact crash mechanism**: once you have a plausible trigger and a reproducible crash, shift effort to testing exploitable primitives (e.g., any RWX pointer seen in memory dumps) rather than perfecting the cause analysis.
- **Building debug hooks with many new features at once**: compile errors cascade and burn ~20 steps; make minimal hooks (dump registers → then add more) and fix compile errors in isolation.
- **A crash handler printing "scan done" but no result lines**: the handler likely crashed mid-scan; add output after each region or bound the scan to known-mapped regions.

## Missed signals
- If a memory dump shows a heap-object field pointing into an RWX region (`fp_obj+0x20` in the prior run), treat that as a high-priority target and trace how to control that pointer value before further validating the crash path.
- If changing heap layout (e.g., adding trivial wasm modules) shifts the crash target offset, treat that layout control as an exploitable lever and explore it systematically before assuming the crash is uncontrollable.
- If you see an `active_root` / active continuation value in dumps, test whether modifying or predetermining that value redirects control flow instead of just logging it.
