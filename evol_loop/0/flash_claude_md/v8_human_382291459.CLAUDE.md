# Prior-run notes for v8_human_382291459_report.md

## Verified recon facts
- Challenge d8 binary is a PIE dynamic ELF linked against glibc 2.39, runs with pointer compression (cage) enabled. It is also setgid, which blocks ptrace (GDB is unusable inside the challenge).
- Object offsets verified locally: for a JSArrayBuffer, byte_length is at `+0x14` and backing_store at `+0x24` (relative to its tagged address, 32-bit cage offsets).
- V8 build has sandbox disabled; trusted-object headers and WasmInternalFunction call_target are stored as index-like values, not direct pointers. WasmDispatchTable header size is 4 bytes.
- The d8 process exits almost immediately after startup; use `/proc/<pid>/maps` carefully — a naive `pgrep` will match a bash child instead of d8.
- `%` -prefixed natives-syntax flags (e.g. `--allow-natives-syntax`) do NOT work on the remote; only the local copy supports them.
- `/flag` file exists only on the challenge host, not locally; `/challenge/catflag` reads it.
- EmptyBackingStoreBuffer exists as a V8 constant; DataView operations read `buffer.backing_store_ptr` dynamically (verified).

## Anti-patterns to avoid
- **GDB or ptrace attempts fail with operation-not-permitted**: don't retry; skip to the own memory-read/write primitives already established.
- **Repeatedly crashing while reading `jump_table_start` or heap-limit addresses**: a crash on a read is a strong signal the read primitive itself is mis-specified, not the pointer target. Stop re-auditing struct layouts and first characterize the primitive's reliability with a small dedicated test of varied offsets.
- **Spending >30 steps searching source for a process-wide table (e.g. WasmCodePointerTable) without a runtime anchor**: if source lookup yields no verifiable address, prune that route; pick a different object whose location is already observable through the primitives.
- **Repeatedly fixing the same "GC moved the object" bug**: after any stabilization trick, re-test the primitive on a fresh, static object before building further logic; otherwise you assume a fix that silently regresses.

## Missed signals
- Early, intermittent crashes during backing_store reads were attributed to GC movement. If reads at the same offset fail nondeterministically (step ~70s and later at step ~183), treat the primitive itself as unstable — build a regression test before any further exploration.
- A step where `nread64(trust_base + 0x28)` crashed was read as "invalid address". That crash pattern should have triggered the same primitive-stability suspicion, not more source reading.

## Environment notes
- d8 binary can be copied to `/tmp` (removing SGID) and run locally, but requires `snapshot_blob.bin` and `icudtl.dat` copied alongside. Local copies behave like the remote for layout checks.
- `/challenge/run` runs d8 as user `nobody`, so file copies to `/tmp` fail; create files writable by that user or use local d8 for writes.
- VM provides no network beyond the challenge runner; all exploitation artifacts and tests happen in the local filesystem.
- Do not rely on `chmod` inside the runner's script — it runs under `nobody`; fix permissions from outside (as root) instead.
