# Prior-run notes for kernel_syzbot_838346b979830606c854_report.md

## Verified recon facts
- The bug triggers via a mismatch between `bpf_prog_attach` and `link_create` validation for CGROUP_SKB attach types, causing a CGROUP_SKB program to be attached to a setsockopt filter; the JIT then interprets the context as `__sk_buff` offsets.
- Confirmed key offsets via gdb: `struct sk_buff` is 240 bytes; `__sk_buff.cb[0]` maps to `sk_buff` offset 0x30; `protocol` at 0xb4; `pkt_type` at 0x80; `mark` at 0xa8; `priority` at 0xac. `struct sock_common` is 136 bytes; `skc_bound_dev_if` lives inside it, not as a direct `sock` member.
- `BPF_SOCKOPT_KERN_BUF_SIZE` is 32 — the on-stack buffer in the setsockopt filter path is only 32 bytes.
- Kernel config lacks `CONFIG_X86_SMEP`/`CONFIG_X86_SMAP`, but `run_vm.sh` passes `+smep+smap` to QEMU. This contradiction was noted but never resolved empirically.
- Accessing `data`/`data_end` in the program requires `CAP_BPF`, unavailable in the initial userns. bpffs is mountable in userns and a BPF token may be creatable, but this path was never tested.
- Container has Internet access (used for searching commits), `/src/linux` contains source only (no git history), and `vmlinux` is available for gdb/objdump.

## Anti-patterns to avoid
- **Disassembling the same function 8+ times across the run**: after each disassembly, save the output to a file and write one line of conclusion next to it; reference that file instead of regenerating the disasm on every new question.
- **Re-running ad-hoc gdb scripts that error on regex or large vmlinux**: normalize on a single batch session with explicit `offsetof` casts; once offsets are extracted, persist them in a scratch file rather than re-querying gdb repeatedly.
- **Searching for a call site with a narrow grep and concluding "not called"**: before abandoning a path, re-grep with broader patterns (e.g., the macro name, not just the function name); the sysctl filter was actually wired up, but the first grep missed it, costing several redundant confirmation steps.
- **Hitting a contradiction between config and runtime (SMEP/SMAP) and just picking a side**: when evidence conflicts, plan one cheap VM experiment to observe the actual runtime state (e.g., reading CR4 via a small program) before continuing pure source analysis.
- **Re-confirming the same structural detail 3-4 times because the analysis wasn't written down**: after any conclusion, write it as a comment in the working file; if a later step seems to contradict it, diff against that comment before re-deriving from scratch.
