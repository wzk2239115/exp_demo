## Anti-patterns to avoid
- **GDB/proc-mem/core-dump attempts all fail about 20 steps**: these debugging routes are blocked by the sandbox; recognize the failure once and pivot to pure JS-side introspection immediately.
- **If every object dumps the same `map` value, don't keep re-dumping more objects**: that is the signal that a base-offset calibration error exists, not a meta-map mystery. Switch to a crash-test to empirically pin the offset.
- **Writing the exploit script by truncating/re-append risks corrupting it repeatedly**: if the script has errors, read the full downloaded/edited file before spawning another edit; prefer line-based truncation over byte-based.
## Missed signals
- The prior run discovered a systematic offset mismatch (`caged_write` writes at `i-4`) early but kept debugging other things; if you find a primitives' argument/offset discrepancy, fix that before investigating object layouts.
- The real object start offset was `addrof-5`; it was found only after a crash-test. If you lack a known-good layout, use crashes to probe offsets early rather than reading more source.
## Environment notes
- The VM kills d8 on `kill -INT`; processes can become zombies, and core dumps are piped to systemd, making them unusable.
- The sandbox blocks compound shell commands; run a single command per invocation.
- ASLR changes cage bases between runs, so hardcoded addresses from one run are not reusable.
- Remote interaction is via HTTP; a local full-chain test with a fake flag is the reliable way to avoid remote round trips.
