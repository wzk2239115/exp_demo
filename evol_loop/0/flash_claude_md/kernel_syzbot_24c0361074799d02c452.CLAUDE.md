## Anti-patterns to avoid
- **Serial socket connects once then dies**: do not retry the same connection; establish a fresh session per command batch, or copy the whole setup to a local VM first.
- **Repeatedly re-testing `mknod`/`mount` under user namespaces**: signal is the same EPERM result; stop after the second confirmation and move to a different access path.
- **Long chroot-escape spirals**: if `getcwd` and mount-ID traces show the current namespace root has no parent mount, abandon escape attempts via path traversal; reformulate the problem in terms of what you can uniquely reach.
- **Local-vs-remote VM drift**: before running exploit attempts, verify the local VM matches the server's mount layout and device list; if not, fix local setup first.
- **Daemon output races**: multiple background shell daemons writing to one log cause truncation races; if output is missing, check for competing processes, then use a single synchronized client.
## Missed signals
- If a downloaded file (e.g., a reproducer) is empty or its output is missing, read it before launching another transfer or search; empty output often indicates a stale connection, not a failed transfer.
- When `ip addr` fails inside the sandbox, treat that as a network-visibility constraint early; do not keep probing connectivity from the same shell.
## Environment notes
- Local QEMU and full root VM work; boot the root shell VM with `init=/bin/bash` only if needed — KVM can Oops on some boot paths.
- QEMU processes become zombies if killed; clean up with `pkill`, but be mindful that `pkill` can also kill the boot script. Verify sockets exist before connecting.
- The server and local VM share the same sandbox restrictions; use local root VM to safely inspect devices and compile, but the real challenge server is only reachable via its serial socket, not by network.
- Root VM `/tmp` is read-only; stages must go to a writable path like `/run`.
