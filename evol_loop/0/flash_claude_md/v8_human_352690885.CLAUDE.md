# Prior-run notes for v8_human_352690885_report.md
## Verified recon facts
- Target is V8 12.4 release build; `/src/v8` contains the buggy source tree (not a git repo).
- Local environment lacks `/flag`, `gc()`, and `print`; network access exists but is flaky/rate-limited.
- Release d8 retains some symbols and supports `--print-bytecode`, `--trace-flush-code`, but not `--print-scopes` or DCHECKs.
- `/src/v8` is source-only; a debug build (with clang at `/src/v8/third_party/llvm-build`) takes many minutes and is worth starting early.
- The challenge's server runs d8 with no flags; `gc()` is unavailable there.
- The relevant bug lives in scope resolution for `super` in arrow functions nested in class members, producing distinct first/second-compilation bytecode (context slot indices differ). A key asymmetry: property set vs get on the wrong home object target different prototype-chain positions.
## Anti-patterns to avoid
- **Web searches for original testcase or issue tracker pages return nothing or an SPA, and GitHub API hits rate limits**: after a couple of failed fetches, stop searching globally and reconstruct testcases locally from source semantics.
- **Repeated experiments with slightly different GC counts / flush flags all yield the same "ERR" (no flip)**: if a flush-related experiment result doesn't change after two parameter tweaks, stop micro-tuning and question the underlying assumption (e.g., "does the arrow actually get discarded?").
- **Deep source audits of the same region more than once (e.g., flushing candidate logic revisited 3+ times)**: before re-reading, write a one-line summary of what you already know and what specifically is still unknown; if nothing is new, switch to empirical probing.
- **Running a matrix test where a helper variable is undefined; spending a step to fix the script and rerun**: inspect a newly-written script for trivial bugs (undefined vars, missing returns) before executing.
- **Interpreting any behavior change as the intended "flip" without bytecode-level verification**: when a test result surprises you, immediately dump bytecode to confirm what actually changed (context slot, source position) before building on it.
## Missed signals
- **A first-call result showing the correct binding in a particular structure was noted but not investigated** to find the trigger that differs from the stable-wrong-binding structure: if you see one structure yielding a different binding direction, isolate which syntactic feature causes it before planning the exploit.
- **A "flip" was observed on plain d8 but then explained away as slot padding without checking whether that padding itself is controllable/an exploitable primitive**: when a non-recompile effect changes behavior, examine what controls the wrongly-read slot's value.
