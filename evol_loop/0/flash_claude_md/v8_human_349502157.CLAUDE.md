## Anti-patterns to avoid
- **Repeatedly re-checking the same source function and concluding it's safe**: if you've verified a bounds-check or a write-site once, stop re-deriving it; instead list it in a fact sheet and move to a different subsystem.
- **Spending many steps on search engines that all fail the same way**: after two consecutive timeouts/empty result sets, stop; switch to googlesource commit logs or GitHub commit-search API (which worked), or pure local source reasoning.
- **Auditing one module (wasm tables) for 150+ steps with no new conclusion**: if no primitive emerges after a bounded survey, record the negative result and pivot to a fresh area (e.g., other object types or historical patch diffs).
- **Treating a localization of a bug-fix commit as the end goal**: after finding the relevant patch, immediately write a minimal probe to test that exact code path in the local challenge binary, rather than continuing broad exploration.
- **Waiting for a full theoretical chain before touching the binary**: if you have symbols and a local `d8`, prefer iterative black-box experiments with small scripts over longer source-only reasoning.

## Missed signals
- If you find a suspicious `field_offset_difference` or similar copy-loop using the **source** object's size instead of the **destination**'s, act on it by writing a test trigger immediately; do not just diff fetched files.
- If you notice the local `d8` is unstripped, leverage that early: use `nm`/`gdb` on the binary (not the running server) and build small harnesses against it, before deep source archaeology.
- If a downloaded CTF repo is large (197MB), extract and grep it for the exact challenge name or related keywords early; it may contain patches, flags, or hints the search engines cannot give.
