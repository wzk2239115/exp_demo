## Anti-patterns to avoid
- **Long source-audit rabbit holes**: repeatedly scanning for consumers of a single field and re-confirming the same conclusion from the docs; after the second confirmation, stop and reformulate the question to what primitive this actually gives you.
- **Waiting on obviously doomed runs**: observing a test still "running" when local scaling data says it exceeds the server's kill threshold; kill it immediately and record the negative result instead of polling output files.
- **Re-testing a known-hard-limit scenario**: designing an experiment whose runtime you already measured exceeds the remote CPU budget; switch to designing probes that fit inside the budget first.
- **Explaining away the same repeated signal**: server kills happen across many different scripts with one consistent cause; each new "is it this script?" probe adds nothing once the discriminator (busy vs sleep time) is found.
- **Local validation when the constraint is remote-only**: a script that takes N seconds locally but must run under the remote budget; skip local full runs and test a scaled-down version on the target.

## Missed signals
- If you find zombie d8 processes consuming CPU during a timed-out compile, that is a strong hint the JIT hang itself is a repeatable outcome — measure what pattern of calls reliably produces it before moving to a new experiment.
- If you find an empty `/challenge/patch` file, verify whether it's truly empty or just unreadable at that moment (e.g., permission issue) before concluding the diff is unavailable.
- If you enumerate globals and find few primitives, consider how each remaining one (e.g., Worker, d8.serializer) interacts with the kernel's process model and SUID context rather than just listing what's missing.
