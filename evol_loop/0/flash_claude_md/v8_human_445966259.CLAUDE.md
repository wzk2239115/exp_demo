## Anti-patterns to avoid
- **Repeatedly re-testing the same wasm UAF hypothesis with slightly different parameters and getting identical "no corruption" results**: step back and stop after one failed confirmation; seek confirmatory evidence (e.g., verify the compiler tier actually changed) instead of escalating input sizes.
- **Spending dozens of steps hand-debugging wasm module binary encodings (section sizes, LEB128, local decl counts)**: when an encoding error persists after 2 fixes, regenerate the module programmatically from a validated in-memory structure rather than patching hex.
- **Long source-diving into builtins (`GetSharedFunctionInfoCode`, DebugBreakTrampoline) that are gated behind an inactive debugger flag**: verify the runtime prerequisite early; if it's not present, drop that line entirely.
- **Entering stress-test mode without checking the GC plan**: adding more fillers/scavenges blindly is not productive; if a forced `%SimulateNewspaceFull` doesn't trigger it, the trigger model is wrong, reformulate it.
- **Ignoring that a test returned "out of bounds" but then continuing to other parameter sweeps**: treat any OOB/potential corruption signal as the highest-priority lead; stop and analyze it immediately.

## Missed signals
- If you see "array element access out of bounds" during a wasm test, that's evidence the UAF may be firing; act on it—attempt to read/write through that stale reference—before testing other configurations.
- If you find a local test that behaves differently from a remote one (e.g., `--allow-natives-syntax` works locally), verify whether the flag is actually honored remotely instead of assuming parity.
- If you download a commit list or diff output, read it fully before spawning a new search; empty results may indicate a tooling bug rather than an empty dataset.
