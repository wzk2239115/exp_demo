# Prior-run notes for v8_human_374790906_report.md

## Verified recon facts
- The remote service runs a custom d8 build with V8 sandbox disabled (`V8_ENABLE_SANDBOX` off); local build matches this. TrustedPointer/ExternalPointer fields are raw addresses, not table indices.
- The provided `pov.js` (≈80KB) is a complete exploit scaffold: it already exposes working primitives (`addrof`, `caged_read`, `caged_write`) via a Wasm type-confusion path. The crash reproduces locally when run unchanged.
- Object layout offsets (verified by dump+Torque source): `JSArrayBuffer` backing_store at +0x24, raw_byte_length around +0x14; `JSDataView`'s write path follows the buffer's backing_store, not its own data_pointer field.
- wasm code pages are mapped RWX in the local process (`/proc/<pid>/maps`), making them a writable+executable target region.
- The container lacks ptrace (`CAP_SYS_PTRACE` absent), so gdb attach fails; memory inspection must use the script's own read primitive or /proc maps.
- `print` is undefined in this d8; only `console.log` works for output.
- Remote server has a hard execution time budget ≈500–700ms per script run; processes killed beyond that.

## Anti-patterns to avoid
- **Repeatedly deep-diving V8 internals (pointer types, Torque layouts) for fields that don't matter in a no-sandbox build**: if static analysis of headers takes >10 min without a payoff, switch to empirical dump-and-check using your read primitive.
- **Using sed on a 2500-line JS file**: multi-edit errors (unterminated strings, missed references like `bytes.map`) caused repeated syntax failures. Prefer generating small test scripts that `require` or append to the base, or do one targeted edit verified by syntax check.
- **Re-sending the same failing remote script hoping for different output**: if a script prints nothing remotely, immediately add staged `console.log` markers with forced flush, or run a trivial marker script to isolate connection vs. runtime issues.
- **Bug-fixing a busy loop via sed**: typos like `while(true){} while(GOOD)` waste steps. Write small test files from scratch rather than patching base.js for quick probes.

## Missed signals
- If you see the local process go zombie/exited while testing, and you need its `/proc` maps, keep it alive with a busy loop *in the same code that spawns it*, not via `setTimeout` (which was found not to hold the process).
- If a remote script runs fine locally but returns empty remotely, treat timeout/task-kill as a primary suspect *before* debugging connection or syntax–measure the remote time budget early with a busy-loop probe.
- If a write via your arbitrary-write seems to land in the wrong place (e.g., bytes read back as all zeros), re-check which pointer the builtin actually dereferences (it was `backing_store`, not `data_pointer`) before assuming your offsets are wrong.
