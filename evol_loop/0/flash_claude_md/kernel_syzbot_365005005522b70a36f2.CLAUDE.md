# Prior-run notes for kernel_syzbot_365005005522b70a36f2_report.md
## Verified recon facts
- The target is the vivid media driver, built-in (not a module), with the bug being a vmalloc out-of-bounds write triggered via V4L2 controls (crop/compose/scaler).
- The buffer being overflowed has a guard page; a direct overflow will crash. KASAN and KFENCE are disabled.
- Kernel source is available at `/src/linux`. The kernel version is 6.14.0-rc2.
- `/dev/video7` on the host maps to `vivid-000-vid-cap`, the relevant target node.
- The jail's `/dev` contains only 5 nodes (null, zero, random, etc.); it lacks any `/dev/video*` nodes.
- `unprivileged_bpf_disabled=0` was observed in the local VM's sysctl.
- `pahole`/debugger verification of struct sizes was not reported; treat any struct layouts as unverified.

## Anti-patterns to avoid
- **Serial connection shows "no output" for many attempts**: verify the kernel command line is correctly formatted before debugging the socket; a single misplaced boot arg causes a silent panic.
- **Repeatedly restarting the VM due to "qemu not running"**: your process-management command (e.g., `pkill`) may be killing your own shell; check the pattern matches only QEMU's own process name.
- **HTTP server "fails to start" without investigation**: immediately check `ss`/`lsof` for the port being already bound; use an uncommon port from the start.
- **Exploring a sandbox-escape direction that keeps yielding "not possible"**: after two distinct methods fail with a capability/mount-namespace root cause, stop that line of inquiry and reformulate the problem around what is in fact reachable inside the jail.
- **Re-verifying the same hard "no" (e.g., `mknod` EPERM) via different system calls**: once the kernel's capability check is traced and understood, treat it as closed; move to designing a trigger that doesn't require those denied operations.

## Missed signals
- If `unprivileged_bpf_disabled=0` is obtained during recon, act on it as a potential attack-surface candidate before spending further steps on device-node creation.
- If `/proc/kallsyms` addresses are all zero (kptr_restrict), note it and move on; do not repeatedly re-check for leaks via other files without a concrete new idea.
- If you see a full `CapBnd` mask inside a user namespace, recognize that `CapEff=full` is normal there and does not grant init-namespace privileges; don't chase this contradiction as a bug.

## Environment notes
- The challenge server's jail environment is identical to the local VM; use the local setup for all testing.
- The VM boots with a custom initrd; you can get a root shell by dropping into initramfs, but the jail's `/dev` is read-only and lacks the video nodes even as root.
- `mknod` for char devices in the jail returns EPERM due to a `CAP_MKNOD` check against the initial user namespace; FIFOs are allowed.
- A TCP6 listener on port 16385 exists on the host but did not respond usefully to a simple `nc` connect.
- Wget/curl inside the jail are dynamically linked and missing required shared libraries; static compilation of transfer tools is the reliable path.
- Outbound internet access from the VM works via QEMU user-mode NAT, and a simple HTTP server can serve files into the jail.
