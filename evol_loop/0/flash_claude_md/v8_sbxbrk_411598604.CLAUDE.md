## Anti-patterns to avoid
- **Repeated polling of a long background build with no new decision**: set a hard time budget; if not done, switch to another actionable track instead of re-checking.
- **Many variant pure-JS GC scripts that all conclude "no crash"**: when the bug requires memory writes, formulate a PoC around the available write API early.
- **Repeated searches for the same "fix commit" across APIs (gitiles/GitHub)**: after two empty/403 results, stop; instead, act on the latest confirmed finding to drive the next hypothesis.
- **Drifting into deep static analysis of list internals for >20 steps without a conclusion**: define an exit condition (e.g., "no new branch after N reads") and pivot to an empirical probe.

## Missed signals
- If you confirm `--sandbox-testing` is enabled and a memory-write API is reachable, treat that as the primary trigger avenue; do not dismiss it as irrelevant because the top-level `Sandbox` object is missing.
- If you find a challenge `patch` file, read it before spawning remote probes or further searches; it may explain constraints quickly.
- If you identify a flag that memory writes can flip to corrupt metadata, build a minimal test around that flip before proceeding to broader audits.
