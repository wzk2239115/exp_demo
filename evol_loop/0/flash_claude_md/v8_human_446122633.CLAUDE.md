# Prior-run notes for v8_human_446122633_report.md

## Verified recon facts
- The d8 binary requires `--experimental-wasm-custom-descriptors` to reproduce the crash; without it the provided PoC path is not active.
- Tooling is minimal: `file`, `gdb` (ptrace blocked), `xxd` are **not** usable. Prefer `Read`/Bash with `od` or custom byte dump loops. `python3` availability was never confirmed.
- The server's `.init` sets `/challenge/catflag` to SUID root and it reads from `/flag`. Running it locally without `/flag` errors with "fopen: No such file or directory", which is a useful beacon.
- The `run` wrapper copies the submitted file to a temp dir as root but the server executes it as `nobody`; `workspace` is not world-traversable. Writeable paths for the payload are `/tmp` only.
- Under the no-sandbox build, the wasm code region is RWX and 512MB in size. Pointer compression cage is 4GB. `kTrustedPointerSize` equals `kTaggedSize` (4 bytes).
- WasmCodePointerTable always exists without sandbox; entries are 8 bytes (no signature hash). `Code.instruction_start` can be read directly via a caged-read, avoiding a need to guess table base.
- The hardened d8 has `print` removed; use `console.log`. Also note `EXIT: exit(0)` from shellcode can hang the process; `exit_group` is the reliable syscall.

## Anti-patterns to avoid
- **Repeatedly spawning `d8` for `/proc/pid/maps` and getting the wrong pid or a "defunct" process**: stop respawning; first verify which process is really d8 (e.g., exact absolute path match) and read maps immediately after fork, or switch to inferring layout from crash addresses + `%DebugPrint`.
- **Trying gdb/`ptrace` attach**: it is forbidden by the sandbox; don't retry after the first `Operation not permitted`.
- **Assuming pointer sizes/field layouts from pre-sandbox intuition**: when a read of a "trusted" field returns a wrong sentinel (e.g., `0xdeadbeef`) or an offset mismatch, stop and re-read the Torque/C++ definitions for the no-sandbox conditional compile paths before further offset patching.
- **Patching the DataView `data_pointer` field**: the accessor actually uses the backing buffer's backing-store pointer; patching a different field causes nread to crash.
- **When shellcode hangs after injection, assuming the injection failed**: first isolate the hang by testing a plain `ud2`/`int3` to confirm code execution, then methodically test syscalls (`write`, `exit_group`, `execve`) one by one; a hang is often a syscall-semantics issue (thread vs process exit), not a write/pointer problem.
- **Streaming large file reads with misaligned byte offsets**: misaligned reads can silently return garbage; keep all reads 4/8-byte aligned.

## Missed signals
- If you find a local binary (`/challenge/catflag`) while building the chain, don't just note it; actually run it (it will fail on missing `/flag`) — its error message and SUID status are your end-goal confirmation and are worth getting early.
- If a logic `%DebugPrint` of a wasm internal shows an unexpected small pointer (e.g., a compressed cage offset) in a field you expect to be absolute, treat it as a signal that the field is still a caged/pointer-compressed value and switch to reading it via your caged-read primitive instead of assuming it is an absolute address.
