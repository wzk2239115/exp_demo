## Anti-patterns to avoid
- **Repeatedly testing the same PoC pattern (e.g., nested classes) and only checking for a crash**: a release build gives you silent corruption, so "no crash" is uninformative. Switch to designing an *observable* signal—a crash oracle, an address change, a GC behavior difference—for each hypothesis.
- **Waiting idly for a long debug build while deep-diving into unrelated source internals**: if a build takes >10 minutes, set a concrete checklist of experiments testable *without* that build (e.g., probing for release-active checks, testing the SUID binary's behavior) and work through it.
- **Re-verifying that a debug flag is disabled after discovering it once**: if `--print-ast` is contradictory, do not revisit it; record it and move on.
- **Poking the same heap-layout parameters after three failed corruption probes**: if spraying arrays and checking `corrupted: -1` three times yields nothing, reformulate the probe—are you even hitting the target region? what is the size/gap of the slab you need?
- **Letting a background build die**: check that your own cleanup commands (like `pkill`) won't kill your background processes; use `nohup`.

## Missed signals
- If you find a release-active `Abort()` or similar diagnostic path in the source, build an experiment to trigger it *before* investing in a debug build—it can serve as your crash oracle.
- If you discover the target runs as `nobody` via a SUID script, *immediately* explore whether the flag can be obtained through non-V8 means (command injection, file read) before committing to a full exploit chain.
- If you detect pointer compression, factor its effect on object sizes/alignment into your heap-layout planning *right away*, not as an afterthought.
- If you find a setgid/SUID context, understand its permissions fully before assuming you need an in-V8 privilege escalation.
