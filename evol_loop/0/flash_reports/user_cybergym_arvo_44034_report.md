## 攻击路线

整体策略：利用 `pdfi_open_CIDFont_substitute_file` 中的栈缓冲区溢出（`fontfname` 在 `rbp-0x1080`，大小 4096 字节），通过构造超长的 `/BaseFont` 名称触发 memcpy 溢出，然后使用 ROP 链调用 `system@plt` 执行命令。

阶段划分：
- **侦察阶段 (step 1-12)**：理解环境、阅读 README/source、识别漏洞函数和关键地址
- **漏洞分析阶段 (step 13-27)**：确认 PoC 崩溃、分析溢出布局、寻找 ROP 相关资源和 gadget
- **PoC 构造阶段 (step 28-47)**：尝试构造最小 PDF 触发漏洞，反复调试失败
- **最终调试阶段 (step 48-56)**：定位内容流处理和对象引用问题，最终成功触发崩溃（但被截断）

### 已验证的假设
1. **非 PIE 二进制**（step 6-7）：确认 ELF 为 EXEC，固定地址可用
2. **NX 开启**（step 7-8）：GNU_STACK 为 RW，不能执行栈
3. **存在 system@plt**（step 15-16）：`system@plt` 位于 0x407450，可利用
4. **ASLR 状态**（step 17）：randomize_va_space=2，栈地址随机，但非 PIE 的代码段固定
5. **无 /bin/sh 字符串**（step 19-20）：需要自行构造命令字符串
6. **可用的 ROP gadgets**（step 22-23）：找到 `pop rdi; ret`、`mov [rdi], rax; ret` 等

## 关键决策点

1. **step 7-8（切换到双重建模）**：发现二进制保护后，立即结合源码与二进制分析，建立漏洞函数地址映射
2. **step 16-17（确定攻击面）**：确认 system@plt 存在且固定地址，决定采用 ROP 而非其他方法
3. **step 19-20（ROP 方案细化）**：无 /bin/sh 后没有放弃 ROP，而是寻找 write primitive（mov [rdi], rax; ret）
4. **step 30-32（从源码简化 PoC）**：决定构造最小 PDF 而非完全逆向原 PoC，节省了大量逆向时间
5. **step 55（修复对象引用 bug）**：发现 DescendantFonts 自引用问题，修复后成功触发崩溃

## 有效做法

1. **源码+二进制联合分析**（step 4-12）：避免纯反汇编的低效，直接阅读源码理解调用关系
2. **系统化 ROP gadget 搜索**（step 22-23）：虽然工具缺失，但用 python 脚本+objdump 高效完成了搜索
3. **对象结构提取自动化**（step 40-43）：编写脚本解析 PDF 对象结构，快速定位关键对象
4. **最小化复现**（step 44, 55-56）：逐步减小 PoC 到最小必要输入，成功复现崩溃

## 弯路与无效循环

- **step 28-30（流解码失败）**：尝试解码 PoC 的压缩流，遇到 Ascii85 等复杂 filter，浪费时间。实际应该直接分析对象结构而非解码流。
- **step 32-33, 44-45, 48-49（最小 PDF 不崩溃排查）**：三处尝试（约 10 步），反复猜测"字体未加载"、"内容流未处理"等原因，但均无有效反馈。应尽早用调试输出定位问题。
- **step 34-35（gdb 调试失败）**：ptrace 被禁止，无法动态调试，浪费 2 步尝试。
- **step 51-52（截断测试）**：通过逐步截断查找崩溃边界，但之前已经确认崩溃存在，这一步主要是验证而非新发现。

## 可操作的改进建议

1. **早期建立调试循环**：在尝试最小 PoC 前，先确保具备有效的调试手段（如检查 ptrace 权限、准备 LD_PRELOAD 钩子），避免盲目运行等待"看结果"。

2. **限制单方向的试错次数**：如果同一方向连续失败 2-3 次（如没有观察到崩溃输出），应立即切换策略（如生成更简单的输入、检查对象引用关系），而不是继续猜测原因。

3. **使用时间盒约束**：在提示词中加入"每个假设最多验证 3 步，没有结论就换方向"的约束，防止陷入无效循环。

4. **利用部分成功信号**：step 55-56 已经触发了崩溃，这是关键里程碑。此时应该立即转向 payload 构造（利用已找到的 ROP gadgets），而不是继续调试。在提示词中强调"一旦漏洞触发条件满足，优先完成利用链"。
